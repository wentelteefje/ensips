# ENSIP-31: Payment Preferences

## Abstract

An ENS name alone does not tell a sender which asset the recipient prefers or which chain to send it on. This ENSIP lets a name publish an ordered list of preferred assets as an [ENSIP-24](./24.md) data record. Each entry is an [ERC-7930](https://eips.ethereum.org/EIPS/eip-7930) Interoperable Address naming one chain and either one token contract on that chain or that chain's native asset. A sender holding an asset selects the first entry it can pay.

## Motivation

ENS resolves a name to an address on a chain the sender has already chosen. [ERC-7828](https://eips.ethereum.org/EIPS/eip-7828) makes that choice explicit in a destination such as `alice.eth@ethereum`, but it does not supply the choice when the sender knows only `alice.eth`.

The preferred chain depends on the asset: a recipient might want USDC on Base and ether on Ethereum. One who holds funds on a single chain, or who accounts for payments in a single asset, needs the sender to pay there, and a payment arriving on a chain the recipient does not monitor may never be seen. This ENSIP lets a name state which assets it prefers, on which chains, and in what order.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 and RFC 8174.

### Payment Preference Record

A name publishes its payment preferences as an [ENSIP-24](./24.md) data record on its own node under the reserved key:

```
payment-preference
```

The value MUST be zero or more entries concatenated with no separator and no framing:

```
E1 || E2 || ... || En
```

Each `Ei` MUST be an ERC-7930 Interoperable Address. Earlier entries rank higher. An absent record and an empty value both mean the name expresses no preference.

### Entries

Each entry names one asset on one chain.

`ChainReferenceLength` MUST NOT be zero. Every entry identifies a chain, so an Interoperable Address with no chain reference is not a valid entry.

`AddressLength` determines what the entry denotes:

| `AddressLength` | Entry denotes |
| --- | --- |
| Zero | The native asset of the chain named by the entry |
| Nonzero | The asset held by the contract at that address on the chain named by the entry |

An entry with a zero-length address is what ERC-7930 calls a Chain Identifier. The native asset is chain-dependent, so such an entry denotes ETH on Ethereum, POL on Polygon, and SOL on Solana. Wrapped forms of a native asset are ordinary contracts and MUST be given as a contract address.

Entries denote fungible assets.

### Parsing

A client reads an entry by walking the value with a cursor:

1. Read 2 bytes as `Version`.
2. Read 2 bytes as `ChainType`.
3. Read 1 byte as `ChainReferenceLength`.
4. Advance `ChainReferenceLength` bytes over `ChainReference`.
5. Read 1 byte as `AddressLength`.
6. Advance `AddressLength` bytes over `Address`.

An entry therefore occupies `6 + ChainReferenceLength + AddressLength` bytes. The client repeats these steps from the start of the value until the value is exhausted.

A value is malformed if any step would read past the end of the value, if an entry has a zero `ChainReferenceLength`, or if the most significant bit of an entry's `Version` is set. ERC-7930 requires that bit to be set when a future version is not backward compatible with its parsing rules, so the length of such an entry cannot be determined and the remainder of the value cannot be located.

A client MUST ignore a malformed value in its entirety and MUST NOT act on the entries it parsed before the failure.

### Selection

A sender selects the first entry in the value that denotes an asset it is able and willing to pay. A name MAY list the same asset on more than one chain, in which case the earlier entry wins. A name MAY also list assets a given sender cannot pay, and a sender that matches no entry has no preference to honour.

Mapping a held asset to the contract addresses that represent it on each chain is the sender's responsibility. This ENSIP does not define that mapping and does not require one to exist onchain.

### Example

A name that prefers USDC on Ethereum, then USDC on Base, then native ETH on Ethereum publishes:

| Entry | Bytes | Length |
| --- | --- | --- |
| USDC on Ethereum | `0x00010000010114a0b86991c6218b36c1d19d4a2e9eb0ce3606eb48` | 27 |
| USDC on Base | `0x0001000002210514833589fcd6edb6e08f4c7c32d4f71b54bda02913` | 28 |
| Native asset of Ethereum | `0x00010000010100` | 7 |

giving a 62-byte value:

```
0x00010000010114a0b86991c6218b36c1d19d4a2e9eb0ce3606eb480001000002210514833589fcd6edb6e08f4c7c32d4f71b54bda0291300010000010100
```

The third entry reads as version `0001`, chain type `0000` for eip155, chain reference length `01`, chain reference `01` for Ethereum, and address length `00`. It carries no address, so it denotes ether.

## Rationale

A token symbol is not unique and anyone can deploy a contract claiming one, so an entry names an asset by the contract that implements it on a particular chain. An Interoperable Address binds those two facts into a single value, which is exactly the pair an entry needs. A sender already knows the contract addresses for the asset it holds, so matching a published list against its own holdings requires no external data and no agreement on what any asset is called.

Entries are concatenated without framing because an Interoperable Address already carries its own lengths. An outer length prefix or an `abi.encode` wrapper would restate what each entry says about itself and multiply the size of a value that is held in storage, where the example above is 62 bytes and `abi.encode(bytes[])` would be 352.

## Backwards Compatibility

This ENSIP adds an [ENSIP-24](./24.md) data record and does not change how ENS addresses or [ERC-7828](https://eips.ethereum.org/EIPS/eip-7828) names are resolved. A client that does not read the record behaves as it does today.

## Security Considerations

A payment preference states what a name says it wants. It does not establish that the named contract holds the asset a sender believes it to be, that the contract is safe to interact with, or that paying it is appropriate. A name can list a contract that is malicious or simply wrong. Clients MUST validate the asset and the recipient before sending funds and MUST NOT treat an entry as an endorsement of the contract it names.

Preferences inherit the security of the name they are published on. Whoever controls the name's resolver and its records controls where senders are directed, which for a subname includes a parent that retains control over it.
